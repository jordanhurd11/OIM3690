Week by Week

The Timeline

Every entry below comes from my actual weekly logs. Click any week to expand what really happened.

I built my personal website with help from AI and learned the absolute basics: creating a repository, committing to main, pushing to origin, and publishing a page. My questions that week say it all — "What does meta mean? What does charset UTF-8 mean? What does rem mean?"

My "what I kept / changed / rejected" note for the first AI interaction was two words: "Kept everything."

I didn't know enough yet to question anything the AI gave me — and honestly, I didn't try.

I created hello.html and about-me.html and learned to add images, links, semantic structure, and proper heading hierarchy.

This was the first week I didn't just accept AI's output. It gave me a page built out of generic containers, and I rewrote it with semantic structure and a real heading hierarchy. I even reused my own code from hello.html to add an image instead of copying the AI's template.

Small moment, but it was the first time I changed the AI's code because I knew a better way.

I turned a full client brief into a landing page for FuelPrep, a budget-friendly meal prep site for college students. First time splitting code into a separate index.html and styles.css instead of one giant file.

I fed the AI the entire brief — audience, pages, style preferences — and it produced the whole site. My note that week was still "kept all code." The specificity of my prompts was growing faster than my ability to edit the results.

I was learning to communicate requirements before I could write the code myself.

I wrote a full Product Requirements Document for FuelPrep — vision, audience, page structure, color palette, typography, brand voice — and had AI rebuild the site from it. The form started saving user inputs to localStorage, the site grew to three pages with consistent navigation, and we did a full semantic HTML and accessibility pass with screen-reader labels and landmarks.

I also shipped the small stuff that makes a site feel real: a custom SVG favicon, Open Graph tags for social previews, and a fix for the mobile hamburger that wasn't hugging the right edge of the screen.

Planning first, then building, produced a far better site than prompting one change at a time.

I presented MP1 to the class, then dove into JavaScript: querySelector, addEventListener, and how HTML, CSS, and JS each play a different role. I also learned to spot the "generic AI look" — endless cards, big rounded corners, default fonts — and that naming exact fonts, colors, and styles gets personalized results.

Then I proposed Mini Project 2: a workout tracker, and my prompts got serious — set-by-set logging, a radar chart drawn with the vanilla Canvas API (no Chart.js allowed), estimated one-rep-max math spelled out formula by formula.

The AI's first version had a bug: workouts weren't actually saving when submitted. I had to go into the code and fix it myself.

That bug was the moment AI stopped being magic. It writes code; I'm responsible for whether it works.

The biggest mental shift of the semester. I wrote in my log: a website is "a system that holds data, transforms it, and redraws itself whenever something changes." When I save a workout, the stats update, the chart redraws, the calendar recolors, and the radar chart shifts — all from one state change.

The tracker grew into a real app: a dashboard with sidebar navigation, a calendar with color-coded planned workouts, an achievements page with Epley-formula personal records, and research-based weekly volume targets per muscle group.

I also started making my own architecture calls — I split each page into its own HTML file for better organization and linked the dashboard calendar with the calendar page myself.

I stopped thinking in pages and started thinking in features and data.

Three small builds: playlist.html (rendering a page from an array of data), fetch-fun.html (an async function fetching random dog images from an API), and post-message.html (sending POST requests with custom headers and a JSON body).

I learned the difference between GET and POST, the three kinds of loops, and a habit that stuck: paste the API URL into the browser and read the raw JSON before writing any code.

When AI extended my playlist, I caught its mistakes — a typo (escapHTML instead of escapeHTML) and blocking alert()/confirm() dialogs, which I removed for a smoother experience.

I was now reviewing AI code the way you'd review a classmate's — trust, but verify.

Mini Project 3: a golf course finder built on the Overpass API. The data was inconsistent — some courses had one field, others had twenty — and the API used POST with its own query language instead of normal GET parameters.

Across three iterations I chained geocoding into course search, added favorites, distance sorting, and a "near me" feature, and handled edge cases I'd never thought about before: rate limits (a real HTTP 429 mid-testing), server errors, denied geolocation, and even a race condition where a slow old search could overwrite a newer one — solved by stamping each request with an ID.

I also learned API keys are like passwords: hide them in a gitignored config file, run git status before every push, and know that only a backend like Vercel truly protects them.

Edge cases are where real apps live. The happy path is the easy part.

Peer review told me my final project idea — a meal prep generator — was too close to projects already presented. So I pivoted to something more unique: a sports betting analyzer. I had Claude write a PRD, split the build into phases, and learned that stating what a project will NOT do is how you stop scope creep.

I fixed two subtle bugs myself this week: a CSS specificity issue where display: grid was overriding the browser's built-in [hidden] style, and a color collision where two teams with the same colors became unreadable — I added a color-distance check that switches the away team to white.

Killing an idea I liked was hard, but the feedback was right — and the new project was better.

Phases 3 through 7 of the sports analyst: live data from multiple APIs (balldontlie for MLB/NBA/NFL/EPL, ESPN for NHL), a Gemini-powered AI analyst, a bet tracker with a clickable bet slip, team stats (injuries, streaks, home/away records), and betting trends with starting vs. live odds.

Best debugging story of the semester: the AI assistant showed "offline" even though my key was fine — Google had retired the model name the AI had coded. I rewrote the proxy to try a chain of model names and remember which one works. I also fixed a UTC date bug that was showing yesterday's games as today's.

By now I was checking the AI's math, having different AI models review each other's code, and asking questions about monetization and multi-model voting systems.

Ten weeks in, AI is a power tool I direct — not a vending machine I wait on.

Final Thoughts

Reflection

Looking back at my logs, the thing that changed most wasn't my code — it was the "What I kept / changed / rejected" line at the bottom of every AI interaction. For the first month it said the same thing over and over: kept everything, kept all, kept all code. I wasn't lying. I genuinely had no basis to change anything.

The turning point was Week 5, when the AI built my workout tracker and workouts silently weren't saving. Nobody was going to fix that for me. Digging into the code to find out why was frustrating, but it taught me more than any working feature had. From then on, the pattern in my logs flips — every week has a bug I found and a fix I made: a typo in a function name, a CSS rule beating the hidden attribute, two teams sharing colors, a retired AI model name, games showing on the wrong day because of UTC.

The other big shift was learning that a website is a system that holds data, transforms it, and redraws itself. Once that clicked in Week 6, everything stopped feeling like separate tricks and started feeling like one machine I could reason about. That's also when my prompts changed — from "make the background light blue" to full PRDs with data structures, formulas, and edge cases spelled out.

I came into this class thinking AI would write websites for me. What I actually learned is harder and more useful: how to plan a product, direct AI with precision, verify what it produces, and fix it when it's wrong. The pivot in Week 9 taught me not to be precious about ideas, and shipping the final project taught me that the last stretch — error states, rate limits, key security, time zones — is where the real work is. Ten weeks ago I couldn't have told you what a meta tag was. Now I want to build systems where multiple AIs check each other's work. That gap is the journey.
